# Ethan 的个人网站

这是 https://ethanyang9512.github.io 的源码。网站放 Ethan 的作品和他做的节目《西湖公园》，以后还会放博客。

它是一个纯静态站：页面由本仓库的生成器提前做好，直接放在 GitHub Pages 上。页面不加载任何外站的脚本、字体和统计，关掉 JavaScript 也能读到全部正文。另外放了给 AI 读的 `llms.txt`，以及 `sitemap.xml`、`robots.txt` 和结构化数据；博客发了第一篇之后，还会生成 RSS。

## 本地构建

需要 Node.js 22 或更新的版本（工作流里用的是 24）。

```sh
npm ci          # 装依赖，只有一个：marked，用来把 Markdown 转成 HTML
npm test        # 跑测试：只用手写的假数据，不联网
npm run build   # 生成到 dist/
```

- 输出目录必须不存在或是空的，否则构建报 `E_OUT_NOT_EMPTY`，什么都不写。`npm run build` 会先用 macOS 自带的 `/usr/bin/trash` 把旧的 `dist/` 移走；在别的系统上，先自己删掉 `dist/`，再运行 `node build.mjs --out dist`。
- 加 `--with-downloads`：从 GitHub 取各作品最新版本的源码包，放进 `downloads/`，作品页的下载按钮就指向本站。取不到的包跳过，只打印一行错误码，那件作品页上不放下载按钮，构建照常完成。源码包不提交进仓库，每次构建时再取。
- 加 `--preview`：站内的目录链接补上 `index.html`，直接用文件方式打开 `dist/` 也能点。
- 构建失败时只打印错误码，不打印原始报错。

## 数据从哪来

网站只搬已经在别处公开的信息，而且只取标题、日期、时长、版本号、链接这类，不转载正文和简介。数字和状态都照来源写，取不到就如实说取不到，不估、不补。

| 内容 | 来源 | 放在 |
|---|---|---|
| 节目单集 | 小宇宙上《西湖公园》的公开节目页 | `data/podcast.json`、`data/seed-episodes.json` |
| 作品的最新版本 | GitHub 上各作品仓库的最新 Release | `data/releases.json` |
| 作品介绍、上架状态 | 作者自己写、自己维护 | `data/works.json` |
| 个人介绍、链接 | 作者自己写 | `data/profile.json` |
| 博客 | 作者写的 Markdown | `content/blog/<slug>.md`，图片放在同名子目录 `<slug>/` |

- 单集按编号（eid）合并，只增不删（小宇宙上删掉的除外，见下一条）。节目页只带最新的一批单集，更早的写在 `data/seed-episodes.json` 里，每次同步一起并入。
- `data/held.json` 列出暂时不展示的项（单集编号、`<仓库>:<版本>`、博客 slug），构建时跳过它们。小宇宙上删掉的单集另记在 `deleted` 里，这一项只由同步增减：节目页给的总期数比上次少，而那期的发布时间在节目页那一批的范围里、页面上却没有了，同步时把它从 `data/podcast.json` 去掉，编号记进 `deleted`；以后哪次节目页上又出现了它（比如那次拿到的是一整页旧缓存），就从 `deleted` 里拿掉，并回 `data/podcast.json`。总期数没变少就不动（页面可能一时不完整）。`episodes`、`releases`、`posts`、`deleted` 缺了哪个都当空清单，在的话必须是字符串数组；格式不对（比如手滑把清单写成了一个字符串，或者内容是 `null`、顶层不是对象）时，构建和每天的同步都报 `E_HELD <键>` 并失败（同步什么都不写），不会当成“没撤下”或空清单；构建失败时部署随之跳过，线上保持上一版。
- 博客文章、新开源的作品这类第一次公开的新内容不会自动搬：先做隐私检查，再由另一个没参与写的审稿人看过，才会提交进这个仓库。

## 每天的同步

工作流是 `.github/workflows/site.yml`，三个任务接力：

1. `sync`：每天 06:17（东八区，UTC 22:17）跑一次，GitHub 的定时任务可能晚几分钟；也可以在 Actions 页面手动运行。依次读小宇宙节目页和 GitHub 的最新版本，写回 `data/`，跑测试；数据有变化才提交一条“同步：日期”，没变化就什么都不提交。测试不过就不提交。两个同步各管各的，一个失败不拖住另一个；有失败的话，这个任务最后标红，整次运行就是红的。
2. `build`：构建网站。每次运行都构建：推送到 `main`、每天定时、手动运行都一样；`sync` 失败时，用仓库里已有的数据。
3. `deploy`：部署到 GitHub Pages。因为每天都会重新构建、部署一次，哪天部署失败了，第二天自动恢复。

几点说明：

- 用工作流自带的令牌推送的提交不会再触发新的运行，所以同步之后在同一个运行里接着构建、部署。
- 仓库是公开的，Actions 日志谁都能看，所以同步脚本只打印期数、编号、版本号和错误码，不打印页面内容。
- GitHub 会停掉 60 天没有任何动静的仓库的定时任务。停了的话，在 Actions 页面重新启用。

## 目录

```
build.mjs            生成器入口：node build.mjs --out dist
lib/                 读数据、渲染页面、生成 llms.txt / sitemap / RSS
scripts/             同步脚本（小宇宙、GitHub 版本）和构建时取源码包
data/                全部内容数据（JSON）
content/blog/        已发布的博客
assets/              样式和图片，原样复制到输出；img/share.png 是分享卡的图（1200×630，照首页首屏的样子截的静态图，首页的大字或配色改了要重做）
test/                测试，夹具全是手写的假数据
.github/workflows/   同步和部署工作流
```
